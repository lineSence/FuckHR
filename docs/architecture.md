# Архитектура

Описание того, что работает сейчас. Нормативные решения и их обоснование — в `wiki/architecture/`.
Где решение на практике заменено другим, это отмечено прямо здесь: ADR остаются историей выбора,
а не описанием кода.

## Контур

Один пользователь, одна машина на Windows (`C:\dev\fuckhr`), всё в RU-сегменте. Внешние адреса — только
hh.ru, сайты отзывов, свой SearXNG, Telegram и адреса моделей. Никакой облачной инфраструктуры и
никакого AI-CLI внутри рантайма.

## Цепочка одного прогона (`run.py`)

```
hh.ru (HTML поиска, ADR-015)
  → зарплатные наблюдения до предфильтра (market.py → market_observations)
  → предфильтр и скоринг (score.py, без модели; метка рынка даёт вес market)
  → страница вакансии (hh_html.py) при включённых деталях
  → слепок в историю (db.vacancy_snapshots, ADR-010)
  → условия из описания (llm_tasks.extract_conditions, этап extract)
  → детектор утверждений (detector.py + detector_llm.py, ADR-009)
  → пересчёт срезов рынка и метки вакансий (market_store.py)
  → досье на компании, прошедшие порог (dossier.py, в несколько потоков)
  → метки работодателей по деньгам (market_company.py)
  → общая оценка работодателя (company_score.py, ADR-018)
  → карточки в Telegram (bot.py)
  → канарейка, если прогон сам сломался (canary.py)
```

Писем в прогоне нет и не будет: контакты и черновики готовит `outreach.py` по явной команде владельца
(`[OUT-006]`, ADR-012, `[CORE-023]`).

## Как собирается досье

```
dossier.build(company)
  → websearch.SearchProvider   поиск по сайтам отзывов (SearXNG / Tavily / Brave), кэш search_cache
  → reviewpage.PageFetcher     чтение самих страниц отзывов, кэш page_cache на 30 дней
  → reviewitems.split_page     страница → отдельные отзывы: дата, оценка, плюсы, минусы
  → reviewlegit.filter_items   отсев не-отзывов: меню, реклама, отзывы клиентов
  → aitext.assess              признак сгенерированного текста (docs/ai-text.md)
  → fake_reviews.score_items   fake_score по сигналам накрутки, без модели
  → fake_company.evaluate      метка компании и средняя без заказных отзывов
  → dossier_text.find_patterns словарь маркеров + учёт отрицаний, без модели
  → dossier_summary.summarize  сводка словами (этап dossier), необязательная
  → company_dossier / company_reviews / review_items / review_hashes
```

Ключевое свойство: флаги и уровень риска считает Python по словарю `PATTERN_RULES`, модель только
пересказывает (`[CORE-015]`). Поэтому досье воспроизводимо и объяснимо: в интерфейсе видно, какая
фраза в каком отзыве дала флаг.

Отзывы, похожие на заказные, не участвуют в средней оценке и в доле негатива, сомнительные идут с
половинным весом; сама накрутка — отдельная метка компании и красный флаг веса 4. Сигналы, пороги и
границы формулировок — `docs/fake-reviews.md`.

## Резюме владельца (B-01)

Резюме — отдельная сущность, а не блок в `profile.yaml`. `profile.yaml` остаётся критериями поиска
(«что ищем»), резюме описывает опыт («кто ищет»).

```
/resume (ui_resume.py)
  → интервью по шести секциям (resume.QUESTIONS)
  → resume_llm.save_draft   один вызов на секцию (этап resume_section), необязательный
  → resume_blocks           текст модели ложится с source='ai', confirmed=0
  → владелец подтверждает блок  → confirmed=1
  → resume.export           Markdown только из подтверждённых блоков
```

Граница одна и жёсткая: наружу — в экспорт и в письма — уходят только блоки с `confirmed = 1`.
Модели разрешено переформулировать ответ и достраивать типовые формулировки, но не факты:
черновик с новым числом отбрасывается целиком (`[CORE-019]`).

Версия под вакансию (`resume_llm.version_for`, этап `resume_tailor`) — это отбор и порядок номеров
блоков, а не новый текст. Текст блока не меняется никогда, поэтому правка блока чинит все
версии сразу, а устаревших копий с ошибкой в дате не остаётся. Повторная вакансия вызова не
стоит: отпечаток состава резюме и текста вакансии лежит в `resume_versions` (`[CORE-016]`).

Без модели работает всё: интервью вырождается в обычную форму, версия под вакансию — в мастер-
резюме целиком (`[CORE-017]`).

Противоречия между резюме и профилем поиска (`resume.contradictions`) показываются как
предупреждения и ничего не блокируют: переход в лиды «через голову» бывает осознанным
решением, а не ошибкой ввода. Стаж считается по множеству месяцев, а не суммой периодов:
две параллельные работы не дают двойного опыта.

## Хранилище

Один файл SQLite (`data/fuckhr.sqlite3`). Таблицы: `intake_log`, `vacancies`, `vacancy_snapshots`, `vacancy_conditions`,
`hr_signals`, `company_dossier`, `company_reviews`, `contacts`, `resumes`, `resume_blocks`,
`resume_versions`, `review_items`, `review_hashes`, `site_lines`, `site_health`, `market_observations`, `market_stats`, `company_market`, `company_score`,
`search_cache`, `page_cache`, `llm_cache`, `embeddings`.

`review_hashes` — общая таблица хэшей на всю базу: она ловит фабрики отзывов, работающие сразу на
несколько компаний, и живёт ровно столько, сколько живут сами отзывы.

Векторов нет: `sqlite-vec` из ADR-008 не подключён, семантический дедуп не нужен на текущих объёмах.
Невосстановимы две вещи: `vacancy_snapshots` — hh.ru не расскажет задним числом, что вакансия висела
в апреле и исчезла в мае, и `resume_blocks` — это ручной ввод владельца, который неоткуда
собрать заново (`maintenance.py` помечает такие цели как опасные).

## Модели

Шлюз `llm.py` знает два адреса: локальный (`LLM_BASE_URL`) и необязательный внешний прокси
(`LLM_PROXY_BASE_URL`). Этап выбирает профиль (`STAGE_PROFILES`), профиль выбирает маршрут.
Этапы `contacts`, `dossier`, `draft`, `review_fake` работают с данными о живых людях и остаются на локальном адресе,
пока владелец не выставит `LLM_PERSONAL_VIA_PROXY=1` (`[CORE-012]`).

Этапы резюме (`resume_section`, `resume_tailor`) в этот список не входят: это данные самого
владельца о себе, и он решает, куда их отправлять; резюме всё равно уйдёт работодателю.

Кэш ответов по хэшу промпта включён всегда (`[LLM-006]`), потолок вызовов за прогон — `LLM_MAX_CALLS`.
Любая ошибка модели возвращает `None`, а не исключение (`[CORE-017]`, `[LLM-009]`).

У этапа не одна модель, а каскад: до трёх кандидатов с прокси в порядке бенча
(`LLM_STAGE_MODELS_<ЭТАП>`, заполняется кнопкой на странице «Модель») и локальный адрес
последним слотом (`llm_cascade.py`, ADR-022). `400`, `404` и `429` выбивают кандидата до конца
прогона без повторов; полный backoff остаётся только у последнего кандидата, ждать которого
больше некого. Кэш ищется по всему каскаду, `LLM_MAX_CALLS` считает попытки, а ответ не от
первого кандидата попадает в лог и в счётчик `Usage.degraded`. У эмбеддингов каскада нет:
модель векторов пиннится (`[LLM-011]`).

Оркестратора нет: `run.py` — обычная последовательность вызовов. LangGraph из ADR-007 не внедрён,
потому что паузы на подтверждение внутри прогона не появилось: подтверждение живёт в `outreach.py`
и в интерфейсе.

## Запуск

Интерфейс и прогон запускаются отдельно. Планировщик Windows запускает `run.py` через `pythonw.exe`
(ADR-014), интерфейс можно держать в фоне тем же способом. Задачи из интерфейса идут подпроцессами:
упавший сбор не уносит с собой страницу, из которой смотришь, почему он упал.

Режим цикла (`RUN_LOOP_ENABLED`, галочка на странице запуска) повторяет прогон целиком:
`RUN_LOOP_CYCLES` кругов, ноль — пока не остановишь. Между кругами пауза `RUN_LOOP_PAUSE`
секунд, настройки перечитываются каждый круг. Цикл обрывается сам, когда hh.ru закрылся
капчей: ходить туда снова — верный способ получить бан подольше. Остановок две: кнопка
«Остановить» убивает процесс сразу, «Остановить после цикла» кладёт `data/stop.flag`
и даёт кругу дописать карточки. Упавший круг не обрывает остальные ([CORE-017]), но
после ошибки пауза не меньше минуты.

Глубокий ресёрч (`docs/deep-research.md`, ADR-019) в прогон не входит: это отдельная задача
`research-deep`, которую владелец запускает кнопкой на странице компании.

`RUN_LIMIT=0` означает сбор без ограничения — до конца выдачи по всем запросам профиля.
Карточек за такой прогон всё равно уходит не больше `run.CARD_LIMIT`.

## Границы

- Западные ATS (Greenhouse, Ashby, Lever) и LinkedIn не поддерживаются.
- Интерфейс слушает только `127.0.0.1`, без авторизации и CSRF-защиты: наружу его выставлять нельзя.
- Резюме заполняется только интервью в интерфейсе: разбора готовых DOCX и PDF нет.
- По данным о людях — только рабочие каналы, никаких личных мобильных, личных соцсетей и покупных баз
  (`[CORE-013]`, `wiki/rules/legal.md`).

## Критерий готовности

Пять вакансий с полным досье за прогон (`[CORE-018]`). Досье считается полным, когда у флагов есть
цитаты из прочитанных отзывов, а не только из заголовков выдачи.

## Где прогон тратит время

Всё дорогое — это ожидание чужих серверов, поэтому лечится оно двумя способами:
не ходить туда вовсе и ходить параллельно.

- Описания вакансий берутся из базы, если они там уже есть и дата публикации не
  менялась (`db.cached_details`). Раньше карточка каждой вакансии качалась на
  каждом прогоне — при тысяче вакансий это почти всё время сбора.
- Пауза между запросами к hh.ru адаптивная: `HH_PAUSE` — верхняя граница и точка
  возврата после капчи, `HH_PAUSE_MIN` — нижняя, до которой пауза сползает на
  чистых ответах.
- Этапы модели (`extract`, `hr_filter`) вынесены из цикла обхода в пул
  (`llm_batch`, `LLM_WORKERS`): внутри цикла каждый вызов на секунды
  останавливал сбор и сбивал ритм пауз.
- Внешний поиск (`websearch.search_many`, `SEARCH_WORKERS`) и страницы отзывов
  (`reviewpage.fetch_many`, `REVIEW_FETCH_WORKERS`) ходят в сеть параллельно.
  Кэш, счётчики и потолки (`SEARCH_MAX_CALLS`, `REVIEW_FETCH_PAGES`) остаются в
  вызывающем потоке: соединение sqlite между потоками не делится, а лимит должен
  считаться один раз.
- Контакты ищутся один раз на компанию, а не на вакансию: страницы «Команда» и
  «Контакты» у всех вакансий работодателя одни и те же, роль берётся по самой
  высокоскоринговой из них.

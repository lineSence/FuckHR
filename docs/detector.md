# Детектор HR-брехни (шаг 3)

Шаг 3 пайплайна: между скорингом и отправкой вакансия проверяется на
соответствие своим же утверждениям (ADR-009).

## Главное правило

Проверяются **утверждения**, а не тон текста [HRD-001]. «Вакансия звучит как
крик о помощи» — не результат. «Заявлена стабильная команда, вакансия
переоткрывалась 5 раз за 8 месяцев» — результат.

Форма вывода всегда одна [HRD-003]:

```
Заявлено: «…дружная команда…»
Найдено: вакансия публиковалась 5 раз за период; возвращалась в выдачу 4 раза
Вывод: утверждение не подтверждается найденными данными (уверенность: высокая)
```

## Настройки

Пороги правятся на странице «Настройки» и живут в `.env`: `DETECTOR_ENABLED`
(выключенный оставляет карточки без HR-флагов, слепки истории пишутся всегда),
`DETECTOR_MIN_DAYS` (сколько дней истории нужно для вывода, по умолчанию 30),
`DETECTOR_REPUBLISH_ALARM` (3), `DETECTOR_WIDE_BAND` (2.0) и `DETECTOR_LLM_CLAIMS`.
Значения ставятся один раз за прогон через `detector.configure` и видны в `detector.LIMITS`;
слишком низкие зажимаются в `settings`, потому что вывод из пустой истории — догадка,
а не наблюдение [CORE-019], [HRD-004].

## Что делает код, а что — модель

`detector.py` — целиком детерминированный Python [CORE-015]:

| Проверка | Источник данных |
| --- | --- |
| «стабильная/дружная команда» | число перепубликаций и возвратов в выдачу |
| «без переработок» | противоречия в том же тексте (стрессоустойчивость, дедлайны) |
| «белая зарплата» | наличие вилки и её изменения между слепками |
| широкая вилка (больше `DETECTOR_WIDE_BAND`, по умолчанию 2×) | поля вакансии |
| грейд против требований | `experience` + senior-токены в тексте |
| висит больше 90 дней | слепки |

`detector_llm.py` — необязательная надстройка. Модель **только предлагает цитату**
утверждения, и цитата проверяется на вхождение в текст вакансии подстрокой.
Пересказ и выдумки отбрасываются. Вердикты и числа модель не производит
[CORE-019]; такие пункты всегда получают статус «недостаточно данных» и в Telegram
не попадают.

## Шлюз к моделям

`llm.py` — единственная точка вызова моделей [CORE-010]:

- профиль выбирается по этапу в `STAGE_PROFILES`, `model="auto"` не используется [LLM-003];
- этапы `contacts`, `dossier`, `draft` жёстко прибиты к `local-only` [CORE-012];
- ответы кэшируются в `llm_cache` по sha256 профиля и промпта [LLM-006];
- есть потолок вызовов `LLM_MAX_CALLS` [LLM-004];
- любая ошибка даёт `None`, а не исключение [CORE-017];
- заголовок `X-Routed-Via` пишется в лог, иначе непонятно, кто ответил.

Переменные: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_TIMEOUT`, `LLM_MAX_CALLS`.
Пустой `LLM_BASE_URL` = шлюз выключен, детектор работает без моделей.

## Где хранятся выводы

Таблица `vacancy_signals(key, created_at, flags, payload)`, создаётся
`detector.ensure_schema()`. `payload` — полный отчёт в JSON, `flags` — список
неподтверждённых утверждений для быстрых выборок.

## Тесты

```powershell
.venv\Scripts\pip install -r requirements-dev.txt
.venv\Scripts\python -m pytest tests/test_detector.py tests/test_llm.py -v
```

Тесты не ходят в сеть: история собирается из слепков во временной SQLite,
а шлюз получает подставной `transport`. Проверять логику на живом прогоне
по сотням вакансий больше не нужно.

## Честное ограничение

До накопления истории детектор почти всегда будет говорить «недостаточно
данных», и это легитимный результат [HRD-004]. Выводы про стабильность команды
требуют не меньше 30 дней наблюдений, а уверенность «высокая» — 60 дней и
трёх слепков с заполненным `published_at`. Если `published_at` на живых данных
окажется пустым (см. issue про корректность `published_at`), сильные выводы по
перепубликациям будут недоступны — это ожидаемо, а не баг детектора.

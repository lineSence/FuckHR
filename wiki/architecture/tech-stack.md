## ADR-006. Язык и стартовая база: Python, адаптеры портируются из career-ops-ui

**Статус:** принято 16.09.2026. **Реализовано**, с одной поправкой: адаптер hh.ru работает
по HTML, а не по Open API (ADR-015). Habr Career пока не портирован.

**Контекст.**
`career-ops-hq/career-ops` (71 800★, MIT) и его форк `Fighter90/career-ops-ui` (69★, MIT) написаны на JavaScript.
career-ops по своей природе — набор skills под AI-CLI (Claude Code, Codex, OpenCode), а не библиотека: его рантайм — внешний
кодовый агент. career-ops-ui добавляет поверх Express + SSE + веб-UI и содержит адаптеры к hh.ru и Habr Career
рядом с ATS-адаптерами Greenhouse / Ashby / Lever.

Прямой форк как основа даёт две проблемы:

1. Ядро завязывается на доступность внешнего AI-CLI, хотя весь смысл FreeLLMAPI — единый собственный endpoint.
2. Оркестратор, structured output, эмбеддинги и текстовая обработка, которые нам нужны, живут в Python-экосистеме.

**Решение.**
Язык системы — **Python 3.11+**. Из `career-ops-ui` берём не каркас, а знание: логика адаптеров **hh.ru** и **Habr Career**
портируется в Python вручную, с сохранением атрибуции по MIT в `NOTICE.md`. ATS-адаптеры (Greenhouse, Ashby, Lever)
не портируются — западные ATS вне нашего контура.

**Следствия.**

- Апстрим career-ops-ui не подтягивается автоматически; адаптеры — наша зона ответственности.
- Ломающиеся адаптеры — ожидаемый регулярный расход, а не авария. См. `[CORE-017]` (деградация, не остановка).
- Отчётная рубрика A–H из career-ops портируется отдельно — см. ADR-009.

**Отвергнуто.**

- *Два процесса (Node-сбор + Python-ядро).* Два рантайма и два набора зависимостей на 16 ГБ ОЗУ, плюс размытая
  граница владения БД.
- *Остаться в Node с LangGraph.js.* Теряется Python-экосистема: rapidfuzz, sentence-transformers, instructor,
  инструменты русской морфологии.

## ADR-007. Оркестратор: LangGraph + langgraph-checkpoint-sqlite

**Статус:** принято 16.09.2026, **не реализовано на 19.09.2026.** Оркестратора в коде нет:
`run.py` — последовательный скрипт, пауза на подтверждение живёт не в графе, а в том, что система
вообще не отправляет писем (ADR-012): черновики готовит `outreach.py` по явному запросу.

**Контекст.**
Пайплайн заканчивается не автоматическим действием, а паузой: человек подтверждает отправку письма (`[CORE-023]`, `[OUT-006]`).
Это human-in-the-loop с сохранением состояния между запусками, иногда на часы или сутки.

**Решение.**
**LangGraph** как оркестратор, состояние — в `langgraph-checkpoint-sqlite`, в том же файле БД, что и данные (ADR-008).
Узлы графа соответствуют этапам пайплайна: сбор → дедуп → извлечение → скоринг → детектор брехни → contact discovery →
черновик → пауза на подтверждение → отправка.

**Следствия.**

- Прерывание и возобновление графа — встроенные, свою очередь задач писать не нужно.
- Плата за это — вес зависимости и её абстракции; читать состояние иногда проще прямо из SQLite.
- Каждый узел обязан быть идемпотентным: повтор после возобновления не должен слать письмо дважды.

**Отвергнуто.**

- *PydanticAI* — легче, но пауза с ожиданием человека решается вручную.
- *Своя state machine на enum-статусах в SQLite* (~200 строк) — дешевле в понимании, но всё ветвление и
  возобновление пишем сами.

> Что вышло на практике: выбран третий путь — пайплайна без состояния вообще. Прогон идёт
> до конца за один запуск и кладёт результат в SQLite, а решения человека — отдельные
> запуски `outreach.py` и действия в интерфейсе. Пересматривать ADR-007 стоит тогда,
> когда появится состояние, которое надо переживать между запусками.

## ADR-008. Хранилище: SQLite + sqlite-vec

**Статус:** принято 16.09.2026 (выбор делегирован владельцем). **Реализовано частично:**
один файл SQLite с WAL — да; `sqlite-vec`, SQLAlchemy/SQLModel и alembic — нет, доступ идёт
через стандартный `sqlite3`, а схема создаётся набором `CREATE TABLE IF NOT EXISTS`
в каждом модуле. Версии схемы и миграций нет — это известный технический долг.

**Контекст.**
Система однопользовательская, пишет один процесс, объём — тысячи вакансий и сотни контактов. При этом 16 ГБ ОЗУ
делятся между Ollama (до ~6 ГБ при загруженной 8B), Chromium для карьерных страниц и самим приложением.

**Решение.**
Один файл **SQLite** + расширение **`sqlite-vec`** для векторного поиска по описаниям вакансий. Доступ через
**SQLAlchemy / SQLModel**, миграции — **alembic**. Чекпойнты LangGraph лежат там же.

**Следствия.**

- Нулевое потребление памяти в простое, бэкап — копирование одного файла, состояние графа и данные согласованы в одной транзакции.
- Включить WAL; при параллельных писателях возможен `database is locked` — писатель должен быть один.
- Если объём вырастет на порядок или понадобится второй писатель, миграция на Postgres остаётся открытой; SQLAlchemy её удешевляет.

**Отвергнуто.**

- *Postgres + pgvector* — +300–500 МБ ОЗУ постоянно, которых нет при живом Chromium; избыточно для одного пользователя.
- *SQLite + Chroma* — второе хранилище и второй формат бэкапа ради того, что делает `sqlite-vec` в том же файле.

## ADR-009. Детектор HR-брехни: словарь клише + детерминированные проверки + рубрика A–H

**Статус:** принято 16.09.2026 (оба варианта, A и B). **Реализовано** — `detector.py`,
`dossier.py`, `dossier_rules.py`. Известное ограничение реализации: признаки ищутся по
подстроке без морфологии, поэтому каждая форма глагола выписывается отдельной строкой.

**Контекст.**
Это ядро ценности проекта: проверка правдивости работодателя до отклика. Ни один из проанализированных аналогов
этого не делает (`wiki/references/prior-art.md`). Покрытие готовыми решениями — около 10%.

**Решение.** Два слоя, оба обязательны.

**Слой 1 — детерминированный (вариант A).** YAML-словарь клише (`молодой дружный коллектив`, `работа в режиме
многозадачности`, `зарплата обсуждается на собеседовании`, `стартап внутри корпорации`) плюс проверки на Python
без участия LLM:

- сколько раз вакансия публиковалась за последние 8 месяцев;
- вилка указана gross или net, указана ли вообще;
- расхождение текста вакансии с отзывами о работодателе;
- возраст вакансии и частота её обновления.

LLM вызывается только по спорным случаям — см. `[CORE-015]` (Python до LLM).

**Слой 2 — рубрика A–H (вариант B).** Структура отчёта и шкала 1–5 портируются из career-ops и служат
форматом вывода: детерминированные флаги слоя 1 ложатся в соответствующие разделы отчёта.

**Следствия.**

- Флаги воспроизводимы и объяснимы: в карточке Telegram видно, какая проверка сработала и на каких данных.
- Словарь клише — живой файл, пополняется вручную по мере наблюдений; это не разовая работа.
- Расход токенов на детектор низкий, так что он может работать в профиле `local-only`.

**Отвергнуто.**

- *Только LLM с промптом-рубрикой* — невоспроизводимо, дорого по токенам, склонно к выдумыванию флагов.

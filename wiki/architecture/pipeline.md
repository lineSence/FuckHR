# Архитектура: пайплайн

Фактическая последовательность одного прогона (`run.py`). Замысел сентября с девятью
абстрактными этапами не реализован и не нужен: шаги совпали иначе.

```
1. COLLECT      hh.ru, HTML поиска (ADR-015) → предфильтр по профилю и настройкам → store
2. SNAPSHOT     слепок в vacancy_snapshots для каждой увиденной вакансии (ADR-010)
3. DETAILS      страница вакансии, если включены описания
4. SCORE        скоринг по profile.yaml, без модели
5. EXTRACT      условия работы из описания (этап extract, необязательный)
6. DETECT       утверждения вакансии против истории публикаций (detector.py, ADR-009)
7. DOSSIER      досье на компании выше порога: поиск → чтение отзывов → маркеры → сводка
8. CONTACTS     рабочие каналы по тем же вакансиям: находки в contact_finds, писем нет
9. NOTIFY       карточки в Telegram: работодатель, утверждения, найденный контакт
10. CANARY      тревога владельцу, если прогон сломался
```

## Настройки этапов

Профиль (`profile.yaml`) отвечает за «что ищем»: запросы, навыки, стоп-слова, вилку.
Настройки (`.env`, страница «Настройки») — за «насколько строго»:

| Ключ | Что меняет |
| --- | --- |
| `PREFILTER_ENABLED` | отсев до загрузки описания; выключенный собирает всё подряд |
| `PREFILTER_MIN_SCORE` | черновой скор, ниже которого вакансия не открывается (скор на выдаче занижен: описания ещё нет) |
| `PREFILTER_FUZZY` | порог нечёткого совпадения навыка, % |
| `DETECTOR_ENABLED` | шаг 6; выключенный оставляет карточки без HR-флагов, слепки пишутся всегда |
| `DETECTOR_MIN_DAYS` | сколько дней истории нужно для вывода `[HRD-004]` |
| `DETECTOR_REPUBLISH_ALARM` | сколько перепубликаций опровергают «стабильную команду» |
| `DETECTOR_WIDE_BAND` | во сколько раз вилка считается фиктивной |
| `DETECTOR_LLM_CLAIMS` | подсказка утверждений моделью; гаснет вместе с `LLM_ENABLED` |

Пороги детектора живут в `detector.LIMITS` и ставятся один раз за прогон
(`detector.configure`); те же значения читает `company_signals`. Значения ниже
разумного зажимаются в `settings`: вывод из пустой истории — догадка, а не факт
`[CORE-019]`.

## Принципы

- Шаги 1, 2, 4, 6 не используют модель вообще `[LLM-005]`, `[CORE-015]`.
- Модель участвует только в трёх местах: `extract`, `hr_filter`, `company`. Все три необязательны:
  с выключенной моделью прогон доходит до конца `[CORE-017]`.
- Сбор с hh.ru строго последователен: паузы между запросами — единственная защита от капчи.
- Досье, наоборот, идёт в несколько потоков (`RESEARCH_WORKERS`, потолок 8): это другие домены
  и другая цена ошибки.
- Порог перед шагом 7 — главный фильтр стоимости: досье и контакты собираются только по интересным офферам.
- Шаг 8 идёт после досье: предусловие `[OUT-002]` проверяется той же функцией, что и при подготовке письма (`outreach.precondition`).
- Свежее досье (младше 30 дней) не пересобирается.
- Идемпотентность держится на кэшах: `search_cache`, `page_cache`, `llm_cache` по хэшу промпта.
- Данные о конкретных людях — только локальной моделью `[CORE-012]`.

## За пределами прогона: письма

Прогон находит контакт, но письма не готовит. Черновик собирается кнопкой «Письмо» рядом
с вакансией в интерфейсе или запуском `outreach.py`, и берёт уже найденные каналы из
`contact_finds` — второй поиск по той же вакансии не оплачивается (`[OUT-006]`, ADR-012). Факты о себе для черновика берутся из подтверждённых блоков резюме
(`resume.facts`), и только при пустом резюме — из блока `facts` в `profile.yaml`. Смешивать
два источника нельзя: получится письмо, где один факт свежий, а второй противоречит ему.
Неподтверждённый текст модели в письмо не попадает никогда `[OUT-005]`, `[CORE-019]`.

## Бюджет

Потолок вызовов модели за прогон — `LLM_MAX_CALLS` (по умолчанию 300), поисковых запросов —
`SEARCH_MAX_CALLS` (60), страниц отзывов на компанию — `REVIEW_FETCH_PAGES` (8).
При исчерпании этап пропускается молча и с записью в лог, а не роняет прогон.

Резюме тратит отдельный бюджет: один вызов на секцию при заполнении и один на версию под
вакансию. Повторная вакансия вызова не стоит: версия кэшируется по отпечатку состава
резюме и текста вакансии в `resume_versions` `[CORE-016]`.

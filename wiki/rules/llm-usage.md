# Правила: работа с LLM и квотами

### [LLM-001] Единая точка входа — FreeLLMAPI
Контекст: любой вызов модели из агентного кода.
Правило: код знает один OpenAI-совместимый endpoint (`base_url` шлюза); список моделей, цепочки и ключи — только в конфиге FreeLLMAPI. LiteLLM остаётся заменой на случай отказа от шлюза.
Статус: validated → core `[CORE-010]`

### [LLM-002] Провайдер не выбирается «один на всё»
Правило: общая цепочка фолбэков для всех шагов — ошибка. Каждый этап работает через свой профиль шлюза (`wiki/architecture/model-routing.md`).
Статус: validated

### [LLM-003] `auto` запрещён на данных о людях
Контекст: смарт-роутинг выбирает провайдера сам, включая обучающихся на промптах.
Правило: этапы contact discovery, досье на людей и черновиков писем идут только через профиль `local-only`. Профиль выбирается кодом по этапу, а не настройкой в дашборде.
Статус: validated → core `[CORE-012]`

### [LLM-004] Каскад по сложности
Правило: дешёвые/быстрые модели отсеивают 80–90% вакансий; сильные работают с оставшимися 10–20%. Лимит «умного» профиля — 100–300 вызовов/день.
Статус: validated

### [LLM-005] Детерминированный код вместо LLM
Правило: зарплатный порог, гео, ключевые слова, дедуп по хэшу описания — обычным Python до любого LLM-вызова.
Статус: validated

### [LLM-006] Кэш по хэшу промпта
Контекст: в мониторинге 60–80% запросов — повторные вакансии.
Правило: кэш ответов шлюза включён всегда — экономит лимиты сильнее любой ротации.
Статус: validated

### [LLM-007] Переключаться до 429
Правило: счётчики шлюза (RPM/RPD/TPM/TPD) — первый рубеж, `tenacity` + `pybreaker` в коде — второй. Один «умный» проход по вакансии = 4–10 вызовов, при 10–30 RPM минутный лимит наступает раньше суточного. Параллелизм 1–2 воркера.
Статус: validated

### [LLM-008] Требования к провайдеру
Правило: провайдер годится, если есть OpenAI-совместимый `/v1/chat/completions`, tool/function calling, JSON-output, внятный RPM (а не только RPD) и стабильный base URL. Доступность из сети владельца проверяется эмпирически через health-check и аналитику шлюза, а не по документации.
Статус: validated

### [LLM-009] Градуальная деградация
Правило: падение, бан или гео-блокировка провайдера снижает качество вывода, но не останавливает пайплайн. Квоты и доступы режут без предупреждения.
Статус: validated → core `[CORE-017]`

### [LLM-010] Локальная модель — последний рубеж, не основа
Правило: облако — основа, Ollama — обязательный последний слот и единственный слот профиля `local-only`. Конкретная модель под железо владельца: `wiki/references/local-models.md`.
Статус: validated

### [LLM-011] Эмбеддинги пиннятся навсегда
Контекст: роутер может отдать `/v1/embeddings` другой модели.
Правило: одна модель эмбеддингов на всю жизнь базы (`bge-m3` локально). Смена модели = полная перевекторизация, иначе поиск тихо деградирует.
Статус: validated

### [LLM-012] Ротация ключей одного провайдера — решение владельца
Контекст: шлюз это умеет; ToS Google/Groq/OpenRouter это запрещают. Владелец решил ToS не учитывать (16.09.2026).
Правило: техническое ограничение снято, но риск остаётся операционным — бан приходит сразу по всем ключам аккаунта и без предупреждения. Поэтому `[LLM-009]` обязателен, а `local-only` должен работать при полной потере облака.
Статус: validated

### [LLM-013] Тег образа шлюза фиксируется
Правило: Docker-образ FreeLLMAPI пиннится по версии, обновление — ручное. Каталог моделей при этом обновляется сам и это нормально.
Статус: validated
